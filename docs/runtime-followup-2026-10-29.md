# 运行时后续修复报告（2026-10-29）

范围：Core `b26354f`、Agent `0215bf3` 之后的三项修复。Core 已提交推送为 `a4cf1cf`；Agent 固定到 `v0.1.1-0.20261029120607-a4cf1cfbd5bb`。本轮没有修改 CLI/TUI/Desktop 功能代码，也没有更改持久化格式或执行真实数据迁移。

## 已实施

### 1. 持续写入失败停止 drain，保留恢复证据

- `drainQueue` 返回错误；协调、认领、目标续跑入队和结果提交错误会阻止 defer 立即重调度。正常退出的队列交接保持原有行为。
- `failQueuedTurn` 将提交失败返回协调层，避免把无法保存失败结果的任务继续当作已经完成处理。
- session event hub 保存本轮 drain 的临时错误并唤醒 `WaitTurn`；不把存储错误写成任务的 durable 终态。下一次明确触发调度时清除临时错误。
- 修正旧行为：`WaitTurn` 遇到提交失败原来可能只等到 context 超时，同步 RunTask 还可能继续在后台等待。现在返回实际存储错误。
- 没有新增自动重试计时器、退避配置或通用故障恢复框架。存储修复后重新打开会话或重新调用 WaitTurn 触发已有协调；已完成 checkpoint 可以补提交，不再次调用模型。

### 2. MCP / Core 关闭拥有唯一清理过程

- MCP Manager 的内部 `Close(ctx)` 在首次调用停止接单、取消连接与 host operations，启动一次清理并保留实例引用。超时只结束调用方等待；并发或重复 Close 等待同一完成信号、返回同一个清理结果。
- 清理等待连接交接、host operations 和 transport 关闭；实例引用在完成后才释放。连接失败和重连路径也真正等待已交出的 stdio transport 关闭，避免在新旧连接交接时失去清理所有权。
- Core 在不可逆资源关闭阶段保持 closing；独立清理过程等待 MCP 完成后才关闭数据库、工具注册表和文件锁。Close 超时后再次调用可以继续等待；完成后返回保存的关闭结果。
- 回归额外发现 CreateSession 缺少关闭检查。现已阻止关闭中创建会话，并把已接受的创建操作计入 sessionOps，使其在存储关闭前完成。

完成通道表示实际完成，不能用来证明不合作的第三方回调已经停止。一个永不退出的回调仍会使清理保持 pending；调用方可以按期限返回，但资源不会被提前释放。

### 3. 用量写入减少中间分配

- 采集 CPU / allocation profile，观察到 JSON 切片增长、文本复制、中间 map 的 RawMessage 解码，以及 SQLite JSON 解析成本；profile 包含初始化和预填充，未将其百分比当成单次写入的精确占比。
- 用量修改只编解码四组用量字段，不再借用完整 Session。
- 五个固定字段组在初始化时构建 SQL；更新 payload 只绑定一次，在语句内部转为 JSONB，按拥有的字段写入。持久数据仍是原来的 JSON BLOB。
- 移除“结果 JSON → map[string]RawMessage → 每字段复制/绑定”的往返。JSON arrow 保留字符串、布尔、数字、数组、对象与 null；新增类型回归防止布尔值被变成数字。
- 未引入缓存、异步记账、拆表迁移或跨版本兼容层。

## 基准证据

同机器顺序运行修改前归档与最终工作树，Go1.27.1，固定 20 次测量、各 5 个样本，取中位数。初始记录数为 0/20/200，在测量过程中继续增长，最多保留 200；这些列表示初始形状，并非全部迭代记录数不变。包括 SQLite WAL/FULL 的文件系统开销。

| 1 KiB / 0 | 3.305 → 2.532 | 27,720 → 19,886 | 127 → 61 |
| 1 KiB / 20 | 3.311 → 3.308 | 60,277 → 49,045 | 128 → 64 |
| 1 KiB / 200 | 4.625 → 4.322 | 399,675 → 352,710 | 138 → 72 |

| 64 KiB / 200 | 4.869 → 4.623 | 406,858 → 360,176 | 138 → 72 |

九组分配字节减少约 11%～30%，分配次数大致减半。多数耗时持平或小幅下降；1 KiB / 0 记录样本下降较大，但本地 I/O 波动明显，不能据此承诺生产环境固定加速。没有宣称恢复了上一轮相对更早 Save 实现的全部耗时差距。

第一轮优化曾让大历史写入变慢，最终改用相关子查询更新，未保留该耗时回退方案。完整原始结果见 [基准记录](benchmarks/runtime-followup-2026-10-29.txt)。

## 验证

- SQLite trigger 持续拒绝完成结果写入：drain 能结束、队列与 checkpoint 保留；解除故障后明确重开会话可以完成，模型调用次数仍为 1。
- 缺失 checkpoint 的 active 队列若无法写失败结果，会停止协调，且不会重放未知副作用。
- 同步 RunTask 返回实际提交错误；上述控制回归在 race 下重复执行。
- MCP 慢 host operation、慢 transport、多个 transport、并发及重复关闭：deadline 返回、引用保留、每个 transport 只关闭一次，最终错误不丢失。
- Core MCP 慢交互：Close 超时后数据库仍可读、不能新建会话，重复 Close 继续等待；交互退出后实际关闭存储。
- 字段写入：跨 Store 并发计数、独立字段保护、删除后不复活、JSON 类型保持、非法 JSON 回滚。
- Core 全量测试与 vet；runtime/session/mcp/tool/command 的 race。Agent 本地 go.work 联动支持包测试、A2A/app/CLI/TUI race 和 vet；Linux amd64/arm64、Windows amd64 CLI/sandbox 构建均带 -trimpath，Windows Desktop 仅编译测试。
